## 第 3/4 梯队代码自审（未修复的债）

对本次交付做了逐文件审查，**无 P0**。确认的缺陷，按严重度：

**P1（建议尽快修）**
1. `AiBreakdownPanel.tsx:50` `crypto.randomUUID()` 无兜底：非安全上下文（`http://<公网IP>:3000`）下 `crypto.randomUUID` 为 undefined，点「确认创建」直接抛错。P0-14/P0-15 计划里明确要用公网 IP 预览，必然踩到。修法：加降级 UUID 生成。
2. `lib/ai.ts:222` `console.error('[ai] 第 N 次调用失败', error)` 打印完整错误对象；AI SDK 的 `APICallError` 带 `requestBodyValues`（`@ai-sdk/provider` 已确认该字段），**会把用户 prompt 写进日志**，与同文件「绝不打印 prompt 内容」的注释自相矛盾。修法：只记 `name/message/statusCode`。

**P2（排期内修）**
3. `lib/issues.ts:153` `columnRows` 查询**缺 `orderBy`** → `appended`（事务期间新出现的卡）顺序随机，并发场景下列内顺序会被打乱且反复抖动。修法：`orderBy: [{ position: 'asc' }, { createdAt: 'desc' }]`；顺带把 `columnRows.some()` 换成 Set（O(n²)→O(n)）。
4. `lib/issues.ts:171` 逐卡 `update` 循环（N+1）：500 张卡的列 = 500 次往返且全程持锁。修法：单条 `UPDATE ... FROM (VALUES ...)`。
5. `Board.tsx:99` `fromIndex === -1` 未处理：若 `onDragOver` 未及触发（快速拖拽、`activeId` 尚未 commit 时 `handleDragOver` 被 72 行守卫提前 return），`reordered` 不含被拖卡片 → 乐观状态停在源列、且服务端只给它改状态不重写 position（落库位置沿用源列旧值）。修法：直接从 `event.active.id` 取 active id（消除 state 竞态），并在 `fromIndex === -1` 时按 `overIndex` 插回目标列。
6. `hooks/useBoardMove.ts:56` 客户端无超时：Server Action 挂死时卡片永久「同步中」禁拖、错误条永不出现。修法：`Promise.race` 加 15s 超时按失败回滚。
7. `lib/rate-limit.ts:16` `buckets` 模块级 Map 只在访问某 key 时清理该 key，**无全局淘汰** → 长期运行内存随用户数增长。修法：定期 sweep 或带上限 + TTL。
8. `scripts/smoke.mjs` 限流用例假设主账号桶为空：**两次运行间隔 <60s 时**，A 的第 3 次调用（timeout 用例）会撞上限额返回 429，断言假失败。修法：AI 功能用例也换每轮新建的账号，或断言容忍 429。
9. `app/api/ai/breakdown/route.ts:51` `await request.json()` 无体积上限（App Router Route Handler 无默认 body 限制）。修法：先查 `content-length`。
10. `lib/ai.ts:108` mock 超时分支只注册 `abort` 监听；若 signal 已 aborted 则 Promise 永不 settle → 挂死。修法：先判 `abortSignal.aborted` 立即 reject。
11. `lib/ai.ts:289` `createIssuesFromSubtasks` 是 Issue 持久化，却住在 `lib/ai.ts` → 内聚性差。建议移到 `lib/issues.ts`。

## 23:03 P0-5 细化方案（产出 `docs/03-development/p0-5-move-issue-bulk-rewrite.md`）

把「整列 SQL 重写」细化到可直接实施：目标列定义、SQL 清单、转换规则、前后对应表、11 条硬约束、18 个边界情况、验证方案、提交拆分、回滚方案。

**核心设计与推导**

- **`fullOrder` 行集合恒等式（方案正确性基础）**：`fullOrder = columnRows ∪ {issueId}`。推得两个结论：① 行集合内所有卡片的最终 `status` 都是 `toStatus`，可整批赋值，**不需要 CASE**；② 行集合无法在 SQL 内重建（顺序来自客户端清单），SQL 只负责「按给定序号落值」。**这否定了「用 `WHERE status = toStatus` 反推行集合」的做法**——那会把步骤 2 之后并发插入的卡片也纳入写集合，破坏等价性。
- **选定写法**：`WITH ordered AS (SELECT id, ord FROM unnest(ARRAY[...]::text[]) WITH ORDINALITY AS t(id, ord)) UPDATE "Issue" AS i SET "position" = ((o.ord-1)*100)::int, "status" = $::"IssueStatus", "updatedAt" = (CURRENT_TIMESTAMP AT TIME ZONE 'UTC') FROM ordered AS o WHERE i."id" = o.id AND i."workspaceId" = $`。`UPDATE ... FROM` 的 JOIN 语义保证行集合**恰为** `fullOrder`。参数 `N + 3`（N=500 → 503），往返 `N+3` → **3**。
- **时区陷阱**：`"updatedAt"` 物理类型是 `TIMESTAMP(3)`（无时区），而 `now()` 返回 `timestamptz`，隐式转换按会话 `TimeZone` 走——非 UTC 会话下会**差 8 小时**。必须写 `AT TIME ZONE 'UTC'`。顺带发现既有隐患：`createdAt` 的库级默认 `DEFAULT CURRENT_TIMESTAMP` 也受会话时区影响，与 Prisma 按 UTC 写的 `updatedAt` 不同源（当前影响为零，因为两者都未渲染到界面）。

# TaskFlow 开发语言与代码规则

## 1. 语言基线

- 业务代码统一使用 TypeScript，不新增 JavaScript 业务文件。
- `tsconfig.json` 必须启用 strict 模式。
- React 组件使用 `.tsx`，纯 TypeScript 模块使用 `.ts`。
- 禁止通过 `any` 绕过类型检查；确需使用时必须在代码审查中说明原因。
- 服务端和客户端共享的数据结构必须有明确类型或 Schema。
- 用户可见文本使用中文；代码标识符和类型名使用英文；提交信息使用中文，格式见 `commit-rules.md`。

## 2. TypeScript 规则

- 优先使用联合类型、字面量类型、泛型和类型守卫表达业务约束。
- 外部输入必须在进入业务逻辑前校验，不能只依赖 TypeScript 类型声明。
- API、Server Action 和数据库边界必须定义输入和返回类型。
- 不使用无意义的类型断言，例如 `value as any`。
- 对可能为空的值显式处理，不使用非必要的 `!` 非空断言。
- 公共函数应让参数和返回值一眼可读，避免过长参数列表。

## 3. React 与 Next.js 规则

- 默认使用 Server Components；只有需要浏览器事件、状态或浏览器 API 时才使用 Client Component。
- `use client` 只放在必要的组件边界，不向上扩散到页面根组件。
- 数据读取优先放在 Server Component，数据变更优先使用 Server Action。
- Server Action 和 API Route 必须执行 Session 校验、权限校验和输入校验。
- 列表渲染使用稳定且唯一的 `key`，禁止使用数组下标代替业务 ID。
- 组件只负责展示和交互；数据访问、校验和业务规则放在 `actions/` 或 `lib/`。
- 不为了“优化”而随意使用 `memo`、`useMemo` 或 `useCallback`，必须有明确的渲染或性能原因。

## 4. 命名规则

| 对象 | 规则 | 示例 |
|---|---|---|
| 变量和函数 | camelCase | `createIssue` |
| React 组件 | PascalCase | `IssueCard` |
| 类型和接口 | PascalCase | `IssueStatus` |
| 常量 | camelCase 或语义化大写 | `issueStatuses` |
| 文件 | kebab-case 或目录既有风格 | `issue-actions.ts` |
| 数据库字段 | Prisma Schema 既有约定 | `workspaceId` |
| 布尔值 | `is`、`has`、`can`、`should` 开头 | `isLoading` |

命名必须表达业务含义，禁止使用 `data1`、`temp`、`handleThing` 等模糊名称。

## 5. 异步与错误处理

- 异步函数统一使用 `async/await`，避免不必要的 Promise 链嵌套。
- 所有外部请求必须处理加载、成功、失败和超时状态。
- AI 请求必须处理无效输出、超时、限流和重试。
- 不吞掉异常；捕获异常后必须记录、转换或向用户返回可理解的错误。
- 防止重复提交和竞态更新，特别是拖拽状态和批量创建场景。
- 错误信息不得包含 API Key、数据库连接串或内部堆栈。

## 6. DOM、事件和表单

- 事件处理函数使用明确的事件类型，如 `React.ChangeEvent<HTMLInputElement>`。
- 只有确有必要时调用 `preventDefault` 或 `stopPropagation`，并记录原因。
- 处理拖拽、键盘和指针事件时，必须考虑无效目标、取消和失败回滚。
- 表单必须同时具备客户端反馈和服务端校验。
- 交互控件必须有可访问名称、焦点状态和键盘操作路径。

## 7. CSS 与 UI 代码

- 优先使用项目现有 Tailwind 约定，不在多个组件中重复相同样式字符串。
- 页面布局必须有稳定尺寸约束，避免加载、错误或长文本导致布局跳动。
- 不引入与当前设计系统冲突的颜色、圆角和阴影风格。
- 响应式规则至少验证桌面端和窄屏端的主要布局。
- UI 组件不承担数据库访问或 AI 调用。

## 8. 注释与文档

- 注释解释“为什么”，不重复代码已经表达的“做什么”。
- 复杂业务规则、外部依赖限制和非直觉决策写入 ADR 或领域文档。
- 对外部 API、Server Action 和公共工具函数，必要时补充使用说明。
- 代码注释可以使用中文；标识符和 API 名称保持英文。

## 9. 测试规则

- 新增业务行为必须同时新增或更新测试。
- 测试名称描述行为和结果，不描述实现细节。
- 优先测试权限、数据校验、状态变更、错误回滚和 AI 输出校验。
- 不为了追求覆盖率而测试框架本身的实现。
- 修复缺陷时必须添加回归测试。

## 10. 依赖和工具规则

- 新增依赖前说明使用场景、替代方案和维护成本。
- 不重复引入已有能力相同的库。
- 依赖升级必须单独提交，并运行 lint、build 和相关测试。
- 不把 AI 生成代码直接视为已验证代码，必须人工审查并运行测试。

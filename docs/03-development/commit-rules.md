# TaskFlow Git 提交规则

## 1. 基本原则

- 每次提交只解决一个明确问题。
- 不提交与当前任务无关的文件、格式化结果或临时产物。
- 提交前必须检查实际变更范围。
- 不提交密钥、个人配置、构建产物和本地运行数据。
- 不为了“让提交看起来干净”而覆盖或删除其他人的修改。

## 2. 分支规则

- `main`：始终保持可构建、可部署。
- `feature/<短名称>`：新功能。
- `fix/<短名称>`：缺陷修复。
- `chore/<短名称>`：工具、依赖或配置调整。
- `docs/<短名称>`：仅文档变更。

一个分支只处理一个 Story、缺陷或技术任务。

## 3. 提交信息格式

提交信息使用中文，**不加 `type(scope):` 英文前缀**（如 `feat(issue):`、`chore(project):`）。`type`、`scope` 仅作为内部分类概念，不写入提交首行。

```text
<一句话说清做了什么>
```

示例：

```text
搭建 Sprint 0 工程基线，含分层目录、Prisma 六表模型与迁移、健康检查接口及依赖清单。
修复看板拖拽失败后状态未回滚的问题，改为按拖拽前快照恢复。
```

提交信息要求：

- 全文使用中文。
- 一句话说清变更结果；确实无法一句话说清时最多两句。
- 只写「做了什么」，不写实现过程。
- 不写提交范围、验证结果、未验证项和风险，这些信息放在自审记录或 PR 描述中。
- 不使用「更新」「修改代码」「临时提交」等无意义描述。
- 行末不加句号以外的多余符号，不堆砌关键词。

## 4. 提交前检查

提交前必须依次执行：

```bash
git status --short
git diff --stat
git diff -- <与当前任务相关的文件>
npm run lint
npm run build
```

如果修改了业务逻辑，还必须运行对应的单元测试和 E2E 测试。

确认以下问题后才能提交：

- [ ] 变更文件全部属于当前任务。
- [ ] 没有误加入编辑器配置、临时日志或截图。
- [ ] 没有提交 `.env`、API Key、Token 或密码。
- [ ] 没有提交 `.next/`、coverage、构建产物或本地数据库文件。
- [ ] 没有把与任务无关的格式化变更混入提交。
- [ ] lint、build 和相关测试通过。
- [ ] 必要的 README、ADR 或测试已同步更新。

## 5. 无关文件处理规则

发现无关文件时：

1. 不要删除用户已有的修改。
2. 不要使用 `git add .` 直接收集全部文件。
3. 只按文件路径添加当前任务所需文件：

```bash
git add docs/03-development/commit-rules.md docs/03-development/development-language-rules.md
```

4. 使用 `git diff --cached --stat` 和 `git diff --cached` 再次确认暂存区。
5. 无关文件保持未暂存状态，不纳入本次提交。

## 6. 提交拆分规则

以下变更应拆成独立提交：

- 功能代码与大规模格式化。
- 数据库 Schema 与无关 UI 调整。
- 测试补充与功能重构。
- 文档更新与业务实现。
- 依赖升级与功能开发。

如果一个 Story 同时包含代码、测试和文档，它们可以在同一提交中，但必须服务于同一个行为变更。

## 7. 提交信息模板

```text
<一句话说清做了什么>
```

- 不要「变更 / 验证 / 风险」三段式，也不要额外补充第二段。
- 提交范围、验证结果、未验证项和风险记录在自审记录或 PR 描述中，不写入提交信息。

## 8. 禁止事项

- 禁止提交包含密钥的文件。
- 禁止提交未验证的数据库迁移。
- 禁止用一次提交混入多个不相关功能。
- 禁止为解决冲突直接覆盖他人或用户的工作区修改。
- 禁止在未检查暂存区的情况下使用 `git commit -am` 或 `git add .`。
